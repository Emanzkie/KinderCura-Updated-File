# KinderCura ML Dataset — `kindercura_assessment_dataset.csv`

This document describes the canonical KinderCura ML training dataset
structure introduced in Step 9. Read this before uploading, retraining, or
citing this file in any report.

## ⚠️ SYNTHETIC / TEST DATA

**`kindercura_assessment_dataset.csv` is entirely synthetic.** It was
generated by `generate_kindercura_dataset.py` for the sole purpose of
exercising the ML pipeline end-to-end (dataset upload → `ml/trainer.py` →
`ml/predict.py` → the centralized staging module). It contains **no real
child, parent, or assessment data**. Do not present results trained on this
file as evidence about real children, and do not describe a model trained on
it as clinically accurate, medically validated, diagnostic, or
representative of real children's development. See "Data leakage" and "Why
real labeled outcomes are eventually required" below for why, even setting
synthetic-ness aside, this dataset cannot support that kind of claim.

## 1. What one row represents

One row = one completed KinderCura developmental screening assessment for
one child, at one point in time — i.e. exactly what a single `Assessment` +
`AssessmentResult` document pair represents in the real application (see
`routes/assessments.js` `POST /submit`).

## 2. Columns

| Column | Meaning |
|---|---|
| `assessment_ref` | A synthetic row identifier (`TEST-001`, `TEST-002`, …). **Not** a real MongoDB `assessmentId` — those are never exported into training data (see "No PII" below). Included only because a stable per-row reference is occasionally useful; safe to drop. |
| `age_months` | Child's age in months at the time of the assessment. Matches the optional `age_months` feature `ml/trainer.py`/`ml/predict.py` already support. Not PII on its own (no birthdate, no identity). |
| `Q01` … `Q34` | One column per KinderCura core-bank assessment question (see "Assessment feature columns" below). |
| `communication_score`, `social_score`, `cognitive_score`, `motor_score` | Per-domain percentage scores, 0–100. Same fields and same formula as `AssessmentResult.{communication,social,cognitive,motor}Score`. |
| `overall_score` | Unweighted average of the four domain scores, rounded — same formula as `routes/assessments.js` `overallScore`. |
| `risk_category` | The ML training **target**: `Low` / `Medium` / `High`. See "Target label" below — **synthetic, not a real outcome.** |

### Assessment feature columns (Q01–Q34)

KinderCura's actual screening has a **fixed bank of 34 core questions**
(`Q01`–`Q34`; see `models/CoreBankQuestion.js` and the `DOCTOR_QUESTION_BANK`
literal in `js/parent/screening.js`, which is still the authoritative
source until the frontend switches to reading the bank from the API). Each
question:

- belongs to exactly one of the four scoring domains: **Communication**,
  **Social Skills**, **Cognitive**, **Motor Skills** (13 motor, 9 social, 6
  communication, 6 cognitive — they add up to 34);
- is gated by a minimum child age (`minAgeMonths`: 36, 42, 48, 60, 72, or
  84) — a parent is never shown a question their child is too young for.

This dataset reproduces that age-gating faithfully: **a `QNN` cell is left
BLANK when the synthetic child was younger than that question's minimum
age**, not filled with a "no" answer. Blank means *not administered*, which
is a real and expected pattern in KinderCura data — a 3-year-old's row will
have many more blank `QNN` columns than an 8-year-old's. `ml/trainer.py`
does not currently use these per-question columns as ML features (see
below) — they are included because a canonical dataset should represent
what an actual completed assessment looks like, and to make the file useful
for any future, richer model that does use item-level responses.

**Custom Questions** (pediatrician-authored, per-child, no stable global id
— see `models/PediaCustomQuestion.js`) are intentionally **excluded**. Only
the fixed, universal 34-question core bank has a stable identifier every
row can share.

## 3. Answer encoding

Every KinderCura core-bank question has exactly three possible answers,
matching the live parent screening UI (`js/parent/screening.js`):

| Stored answer string | UI label | Points (`routes/assessments.js` `scoreAnswer()`) | This dataset |
|---|---|---|---|
| `"yes"` | "Yes, consistently" | 2 | `2` |
| `"sometimes"` | "Sometimes" | 1 | `1` |
| `"no"` | "Not yet" | 0 | `0` |
| *(question not shown — age gate)* | — | — | *(blank)* |

**This is not an invented encoding.** It is the exact numeric transformation
`routes/assessments.js`'s `scoreAnswer()` already applies to every stored
`AssessmentAnswer.answer` string. It is **not** a binary Yes=1/No=0 scheme —
KinderCura's questions are three-way (yes / sometimes / no), and collapsing
"sometimes" into either extreme would throw away real information the
application itself preserves.

A domain's percentage score is `round(sum of that domain's question points
/ (2 × number of that domain's ADMINISTERED questions) × 100)` — i.e.
exactly `routes/assessments.js`'s own formula, computed only over the
questions that weren't blank for that row.

## 4. Score fields

`communication_score`, `social_score`, `cognitive_score`, `motor_score`, and
`overall_score` are the same fields `ml/trainer.py` already requires
(`REQUIRED_SCORE_COLUMNS`) and the same fields stored on every real
`AssessmentResult` document. **No score threshold in this file or its
generator was changed** — `constants/scoring.js`'s 80/60/40 developmental
band cutoffs are untouched and are not reproduced here (this file has no
`developmentalBand` column; that concept is unrelated to the ML target —
see Step 8).

## 5. Target field: `risk_category`

`risk_category` (`Low` / `Medium` / `High`) is what `ml/trainer.py` trains
the RandomForestClassifier to predict, and what `ml/predict.py` outputs. As
of Step 2, `ml/trainer.py` **requires** this column to be present and
explicitly labeled — it will refuse to train on a dataset without it, and it
never derives it from the score columns itself.

**In this file, `risk_category` is synthetic placeholder data — see
`generate_kindercura_dataset.py` for exactly how it was produced.** It is
NOT a real clinical outcome, a real pediatrician's assessment, or drawn from
any real child. It exists only so the training pipeline has something
concrete and schema-correct to run against while KinderCura does not yet
have real, independently-labeled outcomes to train on.

## 6. Data leakage

**If `risk_category` were computed directly from `overall_score` (or any of
the other score columns) by a fixed threshold rule, training a model on
these columns to predict `risk_category` would not discover any clinical
pattern — it would just be re-learning the threshold rule that generated
the label in the first place.** That is target leakage / circular learning,
and any resulting "high accuracy" would be a demonstration of arithmetic,
not of predictive validity.

To avoid presenting exactly that illusion, `generate_kindercura_dataset.py`
deliberately does **not** set `risk_category` as a function of the row's
final scores:

1. Each row's true class is chosen *first*, uniformly at random.
2. Per-question answers are then sampled from a class-conditional
   distribution that **overlaps heavily** between classes (a "Low" row can
   still score fairly low on some questions; a "High" row can still score
   fairly well on some) — see `ANSWER_PROBS` in the generator. This is also
   why this dataset does not exhibit the failure mode the Step 9 task
   explicitly warned against ("Low = all scores high, High = all scores
   low") — the classes are not trivially/perfectly separable by score alone.
3. After scores are computed, **~18% of rows have their label perturbed to
   a neighboring class**, so the final `risk_category` is not a
   deterministic function of the generated scores at all.

This makes the dataset *structurally* free of the most obvious leakage
pattern. It does **not** make the labels clinically meaningful — they are
still fabricated numbers chosen to look like plausible, imperfectly-scored
outcomes, not outcomes anyone actually observed.

## 7. Why real labeled assessment outcomes are eventually required

A model trained on this file can demonstrate that the KinderCura ML
pipeline is **technically functional**: it can load a properly-labeled
dataset, train a RandomForestClassifier, save a compatible model artifact,
and serve predictions that translate correctly through
`constants/developmental-staging.js`. That is a real, useful thing to show
for a thesis defense.

It cannot demonstrate that the model is **clinically valid**. For that,
`risk_category` needs to come from an independent source of truth that
KinderCura does not yet systematically collect at scale — for example,
`models/Assessment.js`'s `clinicalOutcome` field (a pediatrician's
structured review conclusion: `typical_development` / `monitor` /
`referred_for_evaluation` / `confirmed_delay` / `inconclusive`), once enough
real, reviewed assessments exist to build a dataset from. Until then, any
model trained on synthetic data like this file — or on real scores with an
auto-derived label — should be described as a **pipeline demonstration**,
not a clinical tool.

## 8. No personally identifiable information

This file (and its generator) never includes: child name, parent name,
email, phone number, address, or any real MongoDB `_id` (child, parent, or
assessment). `assessment_ref` is a synthetic sequential label
(`TEST-001`, …), not a database identifier.

## Regenerating this file

```
python ml/datasets/generate_kindercura_dataset.py
```

Uses a fixed random seed (`20260819`), so re-running it reproduces the
exact same file. Edit `n_rows`, `ANSWER_PROBS`, or `LABEL_NOISE_RATE` in the
script (not this file) to change the dataset — never hand-edit generated
rows without updating the generator to match.
